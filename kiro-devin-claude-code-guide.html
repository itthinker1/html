CHAPTER 01

目标与架构

1.1目标是什么

目标并不是通过 Claude Code 去创建 Devin 云端开发任务，而是让 Claude Code 自己执行编程 Agent 工作流：

  • 1分析用户目标与当前代码库；
  • 2规划修改步骤并进行多轮推理；
  • 3决定是否调用工具以及使用什么参数；
  • 4由 Claude Code 在本地读取或修改文件、运行终端命令；
  • 5将工具返回结果发回模型，再继续推理，直到任务完成。

三种方案分别使用以下社区项目作为协议适配器：

  • Kiro：d-kuro/kirocc
  • Devin：WncFht/devin2api
  • DevEco：wenyinos/opencode-deveco

1.3谁负责推理，谁负责执行工具？

在这种架构中，模型负责生成推理结果、决定调用工具以及生成调用参数；Claude Code 通常负责执行本地工具。例如，模型提出读取 src/main.ts，Claude Code 读取后把结果回传；模型再提出修改文件或运行测试，Claude Code 执行后继续回传结果。

这不是将 Devin、Kiro 或 DevEco 自己的完整 Agent Harness 搬进 Claude Code，也不等于完全复制原生 Claude 模型的行为。兼容程度仍取决于模型和代理是否正确支持：

  • Anthropic Messages API 请求与响应结构；
  • 流式 SSE 事件；
  • tool_use 与 tool_result 的多轮往返；
  • 推理内容或 extended thinking 的跨轮传递；
  • 模型 ID、上下文长度、图片输入及其他模型能力；
  • 错误状态、限流、超时与重试。
1.4前置条件
  • 1已安装并能正常运行 Claude Code CLI。
  • 2具备相应的 Kiro、Devin 或 DevEco 账号及其允许使用的凭据。
  • 3能在本机启动代理，并访问其环回地址（127.0.0.1）。
  • 4接受模型兼容性可能不完整，重要代码变更需要人工审查与测试。
  • 5DevEco 方案另需 Node.js 20+，以及可登录 DevEco Code 的中国大陆站华为账号。

账号风险、服务条款与公开封号反馈

3.1Kiro：存在明确的官方限制与社区风险信号

Kiro 官方 FAQ 在“可以使用哪些工具”相关条目中说明，Kiro 订阅可以用于 Kiro IDE、Kiro CLI、Kiro Web、Kiro Crew、兼容 ACP 的 IDE，以及某些软件开发自动化场景；但不允许通过 OpenClaw 这类第三方自动化 Harness，将请求路由到 Kiro 原生接口之外。

参考：Kiro 官方 FAQ

这意味着，即使 kirocc 在技术上能把 Anthropic Messages 请求转换给 Kiro 后端，也不能据此认定该接入方式获 Kiro 官方许可。

社区方面，公开讨论中可见一些反代或 Claude Code 相关账号被暂时停用的报告。例如：

  • jwadow/kiro-gateway Issue #115：作者称两个账号被风控，并提到与 Kiro 反代 Claude Code 有关的使用背景；
  • kirodotdev/Kiro Issue #8036：报告中提到 Claude Code、Kiro 与 Omniroute 的组合；
  • kirodotdev/Kiro Issue #9715：用户称在其认为正常的使用情况下遇到临时停用提示。

这些都是用户提交的个案或故障报告，不是官方调查结论，也不能据此计算封号率。它们只能说明：账号停用反馈确实存在，其中部分案例与第三方 Harness 或代理使用有关；另一些报告则不能确认与代理有关。

RISK

风险判断：如需严格遵守 Kiro 服务条款，不应按本节之后的技术步骤将 Kiro 订阅接入 Claude Code；应使用 Kiro 原生 CLI 或官方明确支持的集成方式。本指南仍记录技术流程，是为了说明架构及便于获授权的测试和兼容性研究，不是对该用法的合规背书。

3.2Devin：没有可靠封号率数据，不代表更安全

devin2api 自身声明其为非官方项目、不隶属于 Cognition，并使用 Devin 凭据访问内部 RPC 接口。项目 README 也明确要求使用者自行负责遵守 Devin 的服务条款。

参考：WncFht/devin2api README

Cognition 的 Acceptable Use Policy（页面标注于 2026-06-30 更新）包含不得规避访问控制或安全机制、不得进行未经允许的逆向工程或抓取等限制，并说明违反政策可能导致暂停服务访问。

需要区分两件事：

  • 1Devin 有官方 API，可以用于官方文档规定的任务、会话和开发工作流集成；
  • 2这不等于官方提供了一个通用推理 API，允许把 Devin 内部模型包装成 Claude Code 的模型后端。

本次公开检索没有发现足够可靠、可核实的 devin2api 使用者封号统计，也未找到能够证明其比 Kiro 代理安全的证据。社区样本少、反馈不公开或故障没有被报告，都可能造成“看起来没有封号”的错觉。

RISK

风险判断：Devin 方案的封号发生率无法量化；但由于其调用内部 RPC 的性质和服务政策，不能把它视为无风险，也不建议将重要主账号作为长期生产方案使用。

3.3DevEco：非官方代理，依赖华为账号 OAuth 与内部 MaaS 接口

opencode-deveco 以 MIT 许可开源，项目自身定位为让 opencode 使用 DevEco Code 账号，并未声明与华为的隶属关系或获得官方授权。它通过浏览器完成华为账号 OAuth 登录，随后以 Bearer token 调用 cn.devecostudio.huawei.com 的 codeGenie MaaS 接口。

需要区分两件事：

  • 1DevEco Code 是华为面向开发者的官方产品，账号体系与模型服务由华为提供；
  • 2这不等于华为授权第三方代理把 DevEco 账号包装成 Claude Code 或任意 OpenAI 兼容客户端的模型后端。

公开信息方面，截至 2026-11-26，该仓库约 40 stars、6 forks，没有公开的封号统计或官方支持声明。样本量同样不足以证明“没有风险”，只能说明目前没有可核实的风险反馈。

RISK

风险判断：DevEco 方案的账号风险无法量化；其调用的是华为账号体系与内部 MaaS 接口，且代理自身不做下游鉴权。不应把重要主账号或生产工作流作为长期方案，使用前应自行核对华为 DevEco Code 的服务条款。

方案 A：Kiro → Claude Code CLI

条款

条款提醒：以下是 kirocc 的技术接入示例。Kiro 官方 FAQ 对第三方 Harness 的使用有限制，因此在没有得到 Kiro 明确许可之前，不应将此流程视为受支持的日常使用方法。若严格遵循 Kiro 条款，请改用 Kiro CLI、Kiro IDE，或官方明确支持的 ACP 集成。

4.1项目与工作原理

项目地址：https://github.com/d-kuro/kirocc

kirocc 是本地协议适配代理，项目说明支持：

  • Anthropic Messages API 的 /v1/messages；
  • 流式与非流式请求；
  • /v1/models 模型目录；
  • 将 Anthropic 请求结构转换为 Kiro 后端格式，并将上游事件流转回 Anthropic SSE；
  • 读取 Kiro CLI 本地凭据并刷新令牌，或使用 Kiro API Key；
  • 模型名称映射与部分推理强度选项。

这些是项目公开说明的能力，不代表所有模型、参数及 Claude Code 特性都已经与 Anthropic 原生 API 完全一致。

4.2认证方式

项目 README 列出两种主要来源：

方式 1：Kiro CLI 登录凭据

在本机安装并登录 Kiro CLI，由 kirocc 读取其凭据数据库。优点是不用手动填写 Kiro API Key；缺点是依赖本机 CLI 的登录状态和凭据存储。

方式 2：Kiro API Key

项目 README 说明，符合条件的 Kiro Pro、Pro+、Pro Max 和 Power 订阅用户可以在 Kiro 设置页面创建 API Key；组织订阅还可能需要管理员开启相关设置。

参考：Kiro 官方 FAQ；kirocc README

4.3kiro-cli 安装对 shell 配置文件的改动（dotfiles 集成）
巨坑

此为巨坑：对 ~/.zshrc、~/.zprofile 添加的 hooks 会对 Claude code + herdr app 造成严重的错误，所以要执行后面提到的删除。

kiro-cli 由 Amazon Q CLI（fig 血统）改名而来，自带 kiro-cli integrations 子命令管理"系统集成"，保留着向 shell 配置文件写入 hook 的逻辑。安装或首次启动流程会自动注入 shell 集成，并非只在手动执行 integrations install 时才写入。以下为 v2.33.1（macOS，2026-10-24 安装）的实测结论，不同版本行为可能变化。

实际写入情况
目标安装后说明
~/.zshrc / ~/.zprofile写入 hookzsh 的 pre/post hook 分置于这两个文件；本机已事后手动清除
~/.bashrc / ~/.bash_profile / ~/.profile本机未涉及bash 集成同样会写 .bashrc/.profile，但本机从未存在这些文件
~/.config/fish/conf.d/00_fig_pre.fish、99_fig_post.fish自动创建与 ~/.local/bin 下的符号链接在同一分钟生成；fish 有 conf.d 自动加载机制，无需改 rc 文件
~/.local/bin/ 下符号链接与 PTY 包装二进制自动创建kiro-cli、kiro-cli-chat、kiro-cli-term，以及 zsh (kiro-cli-term) 等包装可执行文件
/usr/local/bin/kiro 路由脚本不创建仅显式执行 kiro-cli integrations install kiro-command-router（需管理员权限）时写入
判断依据（时间线）：
  • 1fish conf.d 两个文件与 kiro-cli 符号链接在同一分钟（10-24 00:34）自动生成，证明安装流程确实自动执行了集成注入，zsh/bash 属于同一套逻辑；
  • 2~/.zshrc 与 ~/.zprofile 的修改时间为 11-08 22:03（相差 6 秒，同一次手动编辑会话），晚于安装时间，与手动清除 hook 的动作吻合；~/.zprofile 清理后为 0 字节；
  • 3~/.zshrc 中残留的 export PATH="$HOME/.local/bin:$PATH" 正是 kiro shell 集成的 PATH 行——kiro 二进制内 fish 文件的原话注释为 # Keeps ~/.local/bin on PATH (previously added by the Kiro CLI shell integration)。
NOTE

重要提醒：kiro-cli integrations status dotfiles 显示的 ✘ 只反映文件的当前内容，不能证明"从未写入"。清除过 hook 之后状态自然回到 ✘。查看状态的命令：

bash查看 dotfiles 集成状态复制
kiro-cli integrations status dotfiles

✔ 表示对应文件当前含有其 hook，✘ 表示当前没有。zsh 条目为 zsh pre post into .zshrc 与 zsh pre post into .zprofile 两条，bash 为 .bashrc/.profile 两条。

写入内容与作用

写入 ~/.zshrc、~/.zprofile、~/.bashrc、~/.profile 的是 kiro-cli init <shell> pre|post 生成的 hook 脚本，作用有三：

  • 1PATH 注入：把 ~/.local/bin 加入 PATH，保证 kiro-cli 系列命令在任意 shell 中可用；
  • 2PTY 包装：在交互式 shell 外层启动 kiro-cli-term（figterm），拦截按键与输出流——这是内联补全、快捷键呼起终端内 chat 的基础；
  • 3会话上下文跟踪：通过 Q_PARENT、Q_TERM 等环境变量识别嵌套会话、tmux、VSCode 任务与非交互 shell，避免在非交互环境中误启动包装。

kiro-cli 平时不驻留 shell，要给"任意终端"提供内联体验，只能在 shell 启动时由 rc 文件（或终端专属集成：iTerm2 脚本、VSCode/Cursor 扩展等）拉起包装器，这就是 dotfile 注入存在的目的。本指南只需要 kiro-cli login 生成凭据供 kirocc 读取，完全不需要这些集成，安装后建议按下方「卸载方法」清除。

卸载方法
bash卸载 dotfiles 集成复制
kiro-cli integrations uninstall dotfiles
  • 卸载是安装的对称回滚：只删除它自己写入的 hook 块与文件，不碰用户其他配置；
  • 集成状态按文件是否存在判定：若已手动删除文件或 hook，命令会返回 Not installed 并跳过（此时卸载动作本身无意义，价值在于留下"用户已卸载"的标记）；
  • 卸载后用 kiro-cli integrations status dotfiles 复核，预期全部显示 ✘。

手动清理同样可行：删除 fish 的 00_fig_pre.fish / 99_fig_post.fish，并从 ~/.zshrc、~/.zprofile 中移除 kiro 注入的 hook 行（PATH 注入行如仍需 ~/.local/bin，可保留）。

卸载影响
影响项结果
kiro-cli chat / login / agent 等命令功能不受影响
凭据数据库（~/Library/Application Support/kiro-cli/data.sqlite3）及 kirocc 读取凭据不受影响
终端内联补全、快捷键呼起 kiro 交互失去（该体验本就依赖此集成）
shell 启动略有改善（不再尝试拉起 PTY 包装）
注意

注意事项：kiro-cli 更新或桌面应用启动时存在自动重装集成的逻辑。如果卸载命令因 hook 已被手动删除而提前返回 Not installed，"用户已卸载"的跳过标记可能未落盘（表现为 ~/Library/Application Support/kiro-cli/settings.json 尚不存在）。若日后发现 hook 或 conf.d 文件再次出现，直接删除即可；或在文件存在时重新执行一次卸载，让该标记正式生效。

6.1项目与工作原理

项目地址：https://github.com/wenyinos/opencode-deveco

opencode-deveco 是一个 TypeScript 编写的本地代理（兼 opencode 插件），把华为 DevEco Code 的账号与模型包装成 OpenAI 兼容端点，并额外提供 Anthropic Messages API 兼容层。它最初服务于 opencode，但 /anthropic/v1/messages 端点同样可供 Claude Code 使用。项目版本 1.3.0，MIT 许可。

实际生效的是本地 HTTP 代理，而不是纯插件：opencode 已发布的二进制不加载外部插件的 auth hooks，因此项目把代理作为真正的接入路径；src/plugin.ts 的 auth hook 仅为前向兼容保留。

代理的主要能力：

  • POST /anthropic/v1/messages：Anthropic Messages API，自动转换为 OpenAI Chat Completions；
  • POST /v2/chat/completions：OpenAI 兼容；默认非流式，显式 "stream": true 才走 SSE；
  • GET /v2/models：动态获取模型列表，失败回退静态列表，缓存 1 小时；
  • GET /v2/login、GET /v2/status、GET /v2/logout：华为 OAuth 登录与登录态；
  • Anthropic 路径支持 tool_use / tool_result、thinking 块、图片与 SSE；
  • tool_choice 会转换为 DevEco 接受的枚举形式（auto / none / required）；
  • max_tokens 透传；上游流中断时补发标准 Anthropic error 事件。
6.2认证方式

仅支持中国大陆站点（siteId=1）的华为账号，与 DevEco Code 上游一致。浏览器打开代理返回的登录地址完成 OAuth：

凭证分三层：

凭证生命周期位置

  • 空闲超时：上游连续沉默 120 秒才中断，不限制总时长。
  • 区域与身份：非中国区账号返回 403；欧洲时区返回 451；未实名账号会收到实名提示。
  • 会话 key：默认以对话首条 user 消息为键，system 提示词变化不会反复新建上游会话；可用 x-session-id 等头显式固定。
  • 代理自身不做下游鉴权，只应绑定 127.0.0.1，不要暴露到公网。
6.9停止
bash停止复制
./svc-opencode-deveco.sh stop

或前台运行时 Ctrl+C；daemon 会一并停止代理。停止后如需彻底清理，可删除 ~/.config/opencode/opencode-deveco/jwt.json。

CHAPTER 07

验证 Claude Code 的推理和工具调用闭环

不要只用“你好”这种普通问答来验证。应分别验证 API、工具调用与多轮推理。

7.1第一级：API 连通性
  • Kiro：GET http://127.0.0.1:3456/v1/models
  • Devin：GET http://127.0.0.1:8080/healthz，再使用下游 Token 调用 GET /v1/models
  • DevEco：GET http://127.0.0.1:17128/v2/status，再调用 GET http://127.0.0.1:17128/v2/models

确认能返回模型目录，且没有持续出现认证或限流错误。

7.2第二级：普通对话

在 Claude Code 中要求模型解释一个已知文件中的函数，并指出对应代码行。检查回答是否确实参考了文件，而不是凭空猜测。

7.3第三级：读取文件与工具结果回传

在一个测试仓库中，要求 Claude Code：

  • 1读取一个指定源文件；
  • 2总结一个小函数当前的行为；
  • 3根据源文件而不是凭空假设，指出一个低风险改进点。

确认 Claude Code 真实执行了读取工具，并将文件内容回传给模型。

7.4第四级：受控写入与测试

使用 Git 工作分支或一次性测试目录，要求它修改一个无关紧要的字符串或一个简单测试，然后运行指定的测试命令。检查：

  • 模型是否给出合适的工具调用；
  • Claude Code 是否成功执行；
  • 工具结果是否传回模型；
  • 模型是否根据测试结果继续推理；
  • 文件改动是否合理、可撤销。
注意

不要直接在生产仓库做第一次验证。首次测试时限制权限，重要命令由人工确认。

7.5第五级：多轮工具调用与较长任务

测试连续的“读取 → 修改 → 测试 → 根据错误修复”流程。若任务中途停顿，分别检查 Claude Code、代理日志与上游服务的错误时间，不要立刻重复提交造成额度消耗。

7.6验收清单
验收项通过标准

流式响应输出可以持续到达，没有频繁中断或 SSE 解析错误

CHAPTER 08

常见故障排查

8.1连接失败 / Connection refused

检查代理是否启动、端口是否正确、服务是否只监听 127.0.0.1，以及 Claude Code 所在环境能否访问该地址。Docker 环境中的 localhost 指向容器自身，需要按容器网络架构设置转发地址。

8.2401 Unauthorized

Kiro：

  • 是否把上游 Kiro Key 与代理自身的 KIROCC_API_KEY 混淆；
  • 是否需要重新登录 Kiro CLI；
  • Key 是否撤销或账号是否有相应订阅权限；
  • 客户端传的 ANTHROPIC_AUTH_TOKEN 是否与代理要求一致。

Devin：

  • 是否使用下游代理 Token，而不是 cog_... 上游 Key；
  • Token 是否在 /web/tokens.html 创建且仍有效；
  • 上游凭据是否已失效或被撤销；
  • 账户配置是否加载成功。

DevEco：

  • 是否完成华为 OAuth 登录（GET /v2/status 应返回 logged_in:true）；
  • ANTHROPIC_API_KEY 是否为占位值 opencode-oauth-dummy-key（代理不做下游鉴权，真实 token 由代理注入）；
  • jwtToken 是否失效（~/.config/opencode/opencode-deveco/jwt.json），必要时重新访问 /v2/login；
  • ANTHROPIC_BASE_URL 是否带 /anthropic 前缀。
8.3403 / 账号暂时停用

对 Kiro，若返回“User ID temporarily suspended”或类似安全锁定消息，应停止通过代理发起请求，保存 Request ID 与发生时间，并按官方支持渠道处理。不要尝试以更换账号、伪装网络或自动轮换凭据来规避。

对 Devin，若上游拒绝认证或限制访问，先查看代理返回的错误阶段与官方账户状态；不要连续高频重试或尝试绕过服务端限制。

8.4429 Too Many Requests

可能是客户端重复请求、本地代理并发限制、上游速率限制或套餐额度问题。查看 Retry-After（如果存在）、代理日志和上游账户用量。降低并发与重复重试，等限制窗口结束后再测试。不要把 429 误认成封号证据。

8.5能回答文本，但工具调用失败

这种情况常见于协议只有部分兼容。检查：

  • 当前后端模型是否支持工具调用；
  • 代理是否能保留 tool_use 与 tool_result 的对应关系；
  • 工具结果是否被完整返回；
  • 模型是否正确处理结束原因与多轮对话；
  • 当前模型是否支持所请求的推理、图片或搜索功能。

优先使用小型、单工具测试重现问题，不要一开始就用复杂的多代理任务。

8.6Devin 返回 unavailable

当前 devin2api README 说明，空的上游账户池可能导致接口返回 unavailable。前往 /web/accounts.html 检查是否存在可用的上游账户及其认证状态。

8.7流式输出停住

检查代理日志、上游状态、客户端总超时和网络连接。项目可能会为某些状态返回重试提示，也可能因客户端总超时而提前结束。避免同时开多个相同请求，防止重复耗费额度。

8.8模型列表里没有预期模型
  • 查询 /v1/models 的真实输出；
  • 确认上游账号有该模型的访问权；
  • 检查模型别名配置与代理版本；
  • 对 Claude Code 先显式指定实际模型 ID，再排查模型选择器发现机制。
8.9DevEco 常见问题
  • 401 / 未登录：先访问 GET /v2/login 完成华为 OAuth；/v2/status 显示 logged_in:false 时，请求会返回 401 并附登录 URL。
  • 403 / 非中国区或未实名：代理只接受中国大陆站（siteId=1）华为账号；非中国区返回 403，未实名账号会收到实名提示。
  • 451：欧洲时区（含官方列表里的俄罗斯/中亚特例）的推理请求会被直接拒绝，与官方客户端行为一致。
  • 429 / 队列满：DEVECO_MAX_CONCURRENCY 默认 1、DEVECO_MAX_QUEUE 默认 3，突发请求会排队或直接 429；降低并发或调大队列，不要高频重试。
  • 长回复中途 Upstream stream ended early：上游连续沉默超过 120 秒才会中断；重试或压缩对话历史，不要误判为账号问题。
  • 模型不存在 / ProviderModelNotFoundError：模型 id 必须精确写成 GLM-5.1 / GLM-5.3（不是 glm-5）；deepseek-v4-flash 不在动态列表，需要手工指定。
  • 第二个实例刷新失败：同一 jwtToken 不支持两个进程并发刷新，只能保留一个代理；先停掉旧实例再启动。
  • /v2 前缀：所有端点均可省略 /v2（如 GET /status）；Claude Code 使用的 Anthropic 路径是 /anthropic/v1/messages。

CHAPTER 09

凭据、日志与项目安全

9.1明确区分两层凭据
方案上游凭据Claude Code 使用的下游凭据
KiroKiro CLI 凭据或 KIRO_API_KEY代理没有启用客户端鉴权时可能是占位令牌；启用时使用 KIROCC_API_KEY
DevinDevin 平台 API Key、会话 Token 或凭据文件在本地管理面板创建的 devin2api 下游 Token
DevEco华为账号 OAuth：jwtToken（~/.config/opencode/opencode-deveco/jwt.json，0600）与内存 accessToken占位 API Key opencode-oauth-dummy-key；代理不做下游鉴权

上下游凭据不应混用。任何一个泄露都可能造成账号接管、额度消耗或未经授权的调用。

9.2本地网络暴露
  • 默认绑定 127.0.0.1；
  • 不要映射到公网或局域网，除非已设计鉴权、TLS、防火墙与访问控制；
  • 不要把空密码的管理面板暴露到非可信网络；
  • 不要因排障方便而关闭代理鉴权后忘记恢复；
  • 如果需要从容器或其他设备访问，先单独设计网络安全配置，不要简单改为 0.0.0.0；
  • DevEco 代理自身不做下游鉴权，只应绑定 127.0.0.1；无头登录用的 SSH 隧道也只转发 loopback 端口。
9.3日志与代码隐私

代理可能接触到完整提示词、代码片段、工具调用参数和工具返回结果。处理商业代码、客户数据或秘密时：

  • 1关闭调试日志与不必要的遥测；
  • 2检查日志目录及保留时长；
  • 3避免启用包含请求或响应正文的追踪功能；
  • 4不要上传含有令牌的日志；
  • 5不要将 .env、config.yaml、数据库或凭据文件提交到 Git；
  • 6对代理源码进行审计，尤其是网络请求目的地、日志和更新机制。

DevEco 代理的日志（opencode-deveco.log）记录模型、耗时与 token 用量，不记录请求正文；可用 DEVECO_LOG_LEVEL 控制详细程度。jwt.json 是明文长效凭据，应与密码同等保护。

9.4更新与供应链
  • 固定一个已经验证的 release 版本，而不是不审查地自动跟随最新版本；
  • 更新前先检查 release notes 与源代码变化；
  • 从官方 GitHub 仓库下载，并核对项目提供的 SHA-256 校验文件（如有）；
  • 保留可回滚的版本和配置备份；
  • 对会自动更新的常驻服务，了解其二进制替换和重启逻辑；
  • DevEco 为本地 TypeScript 构建，使用仓库的 package-lock.json 固定依赖；从官方仓库拉取并审阅 src/proxy.ts 的转发目的地与日志逻辑。

升级、停用与回滚

10.1临时停止
  • 前台启动的进程：用 Ctrl+C 正常结束；
  • Devin 托管部署：按当前项目 README 的 status、uninstall 或服务管理命令操作；
  • Kiro：若使用 launchd、其他守护进程或容器，请按相应方式停止；
  • DevEco：./svc-opencode-deveco.sh stop（先停 daemon，再停监听进程）。
10.2停用后清理
  • 1停止代理服务；
  • 2撤销不再需要的上游 API Key；
  • 3删除或停用代理下游 Token；
  • 4清除 shell 环境变量；
  • 5清理存有敏感数据的调试日志和配置备份；
  • 6若曾将令牌写入 Git，立即撤销令牌并清理仓库历史（单纯删除文件并不能使已泄露令牌失效）；
  • 7DevEco 方案还需删除 ~/.config/opencode/opencode-deveco/jwt.json，并移除本地 dist/ 构建产物或整个克隆目录。
10.3回到 Claude Code 原来的模型服务

本指南使用临时 env ... claude 的方式启动，可以在当前会话结束后直接恢复平时的终端环境。若你曾在 ~/.zshrc、~/.bashrc 或 ~/.claude/settings.json 中写入代理地址，请删除或还原对应设置，并开一个新终端验证。

检查当前环境是否还残留代理变量：

bash检查残留变量复制
printf 'ANTHROPIC_BASE_URL=%s\n' "${ANTHROPIC_BASE_URL:-<unset>}"
printf 'ANTHROPIC_MODEL=%s\n' "${ANTHROPIC_MODEL:-<unset>}"

不要在不确认原值的情况下直接覆盖个人配置。若原来使用其他 API 网关，应按备份内容恢复。

最终建议

如果最终目标是稳定地在 Claude Code 中使用其他模型，并保留完整的推理与工具调用能力，建议按以下原则决策：

  • 1优先考虑官方允许的 API 或集成机制。这是减少账号风险与内部接口变更风险的最有效方式。
  • 2不要把 Kiro 反代直接当作长期主力。Kiro 官方 FAQ 已明确限制第三方 Harness 将请求路由到原生接口之外；公开社区也出现了相关账号停用报告。
  • 3不要因为暂时没看到 Devin 封号报告就认为 Devin 更安全。devin2api 使用内部 RPC；官方政策也存在逆向工程与访问控制限制。没有可靠统计就不能推导封号率。
  • 4先验证工具闭环再评价实际编程效果。文本回答只是最低门槛；必须实测工具调用、多轮回传、流式输出、测试修复流程、稳定性和用量。
  • 5主账号、重要代码与生产任务应优先选择可获得官方支持的方式。对非官方代理，限定在隔离测试环境，并准备随时停用与撤销凭据。
  • 6DevEco 方案同样属于非官方适配。代理使用华为账号 OAuth 和内部 MaaS 接口，且自身不做下游鉴权；只应在隔离环境使用，并严格绑定 127.0.0.1。
决策摘要
  • 若服务条款合规是前提：不要使用未经允许的 Kiro 反代；Devin 与 DevEco 也应先确认服务方对第三方代理的许可。
  • 若目标是技术研究：可在隔离环境评估三个适配器，但应把账号停用、额度损失、隐私泄露及上游协议变化纳入成本。
  • 若目标是长期生产使用：优先改接官方文档明确支持的推理 API 或网关，而非依赖内部 RPC、OAuth 包装或桌面应用凭据。
